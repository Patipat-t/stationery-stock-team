# Spec: ฟีเจอร์แจ้งเตือนสต็อกต่ำ และรายงานมูลค่าสต็อก

## 1. เป้าหมาย (Goal)
เพิ่มความสามารถให้ระบบ inventory แจ้งเตือนผู้จัดการเมื่อสินค้าใดมีสต็อกต่ำกว่า threshold และให้ผู้จัดการดูรายงานมูลค่าสต็อกแยกตามหมวดหมู่ได้

## 2. User Story

| รหัส | User Story |
|---|---|
| US-01 | As a พนักงานคลังสินค้า, I want บันทึกการรับ/จ่ายสินค้าพร้อมอัปเดตสต็อกทันที, so that สต็อกในระบบสะท้อนจำนวนจริง |
| US-02 | As a ผู้จัดการ, I want รับการแจ้งเตือนทันทีเมื่อสินค้าใดต่ำกว่า threshold, so that สั่งซื้อได้ก่อนของหมด |
| US-03 | As a ผู้จัดการ, I want ดูมูลค่ารวมของสต็อกแยกตามหมวดหมู่, so that ตัดสินใจด้านการเงินได้ |
| US-04 | As a ผู้จัดการ, I want กำหนดค่า threshold สต็อกต่ำแยกรายสินค้าได้, so that เหมาะสมกับอัตราการใช้งานของสินค้าแต่ละชนิด |
| US-05 | As a ผู้จัดการ, I want เลือกลงทะเบียนช่องทางการแจ้งเตือน (Email, SMS) ได้หลายช่องทางพร้อมกัน, so that ได้รับข้อมูลผ่านช่องทางที่สะดวก |

## 3. Acceptance Criteria (Given-When-Then)

### AC ของ US-01: บันทึกรับ/จ่ายสินค้า
```gherkin
Scenario: รับสินค้าเข้าคลังสำเร็จ
  Given สินค้า "ท่อ PVC 1/2 นิ้ว" มีสต็อกปัจจุบัน 10 ชิ้น
  When พนักงานบันทึกรับเข้า 15 ชิ้น
  Then สต็อกคงเหลือกลายเป็น 25 ชิ้น

Scenario: จ่ายสินค้าเมื่อสต็อกไม่เพียงพอ
  Given สินค้า "ท่อ PVC 1/2 นิ้ว" มีสต็อกปัจจุบัน 5 ชิ้น
  When พนักงานพยายามบันทึกจ่ายออก 10 ชิ้น
  Then ระบบต้องปฏิเสธรายการและแสดงข้อผิดพลาดว่าสินค้าไม่เพียงพอ
  And สต็อกคงเหลือยังคงเป็น 5 ชิ้นเท่าเดิม
```

### AC ของ US-02: แจ้งเตือนสต็อกต่ำกว่า threshold
```gherkin
Scenario: จ่ายสินค้าจนสต็อกต่ำกว่า threshold
  Given สินค้า "สายไฟ 2.5 sq.mm" มีสต็อก 20 เมตร และ threshold = 15
  When พนักงานบันทึกจ่ายออก 8 เมตร
  Then สต็อกคงเหลือ 12 เมตร
  And ระบบส่งการแจ้งเตือนถึงผู้จัดการว่าสต็อกต่ำ

Scenario: จ่ายสินค้าโดยสต็อกเท่ากับ threshold พอดี (Edge Case)
  Given สินค้า "สายไฟ 2.5 sq.mm" มีสต็อก 20 เมตร และ threshold = 15
  When พนักงานบันทึกจ่ายออก 5 เมตร
  Then สต็อกคงเหลือ 15 เมตร
  And ระบบต้องไม่ส่งการแจ้งเตือน

Scenario: จ่ายสินค้าโดยสต็อกยังสูงกว่า threshold
  Given สินค้า "สายไฟ 2.5 sq.mm" มีสต็อก 50 เมตร และ threshold = 15
  When พนักงานบันทึกจ่ายออก 10 เมตร
  Then สต็อกคงเหลือ 40 เมตร
  And ระบบต้องไม่ส่งการแจ้งเตือน
```

### AC ของ US-03: รายงานมูลค่าสต็อกแยกตามหมวดหมู่
```gherkin
Scenario: คำนวณมูลค่ารวมแยกตามหมวดหมู่ที่มีสินค้า
  Given มีสินค้าหมวด "ไฟฟ้า" 2 รายการ ได้แก่ สายไฟ (10 ชิ้น ราคาชิ้นละ 100 บาท) และเบรกเกอร์ (5 ชิ้น ราคาชิ้นละ 200 บาท)
  When ผู้จัดการเรียกดูรายงานมูลค่าสต็อกแยกตามหมวดหมู่
  Then ระบบแสดงมูลค่ารวมของหมวด "ไฟฟ้า" เท่ากับ 2,000.0 บาท

Scenario: รายงานหมวดหมู่ที่ไม่มีสินค้าคงเหลือ
  Given หมวดหมู่ "ประปา" ไม่มีรายการสินค้าคงคลังคงเหลือในระบบ
  When ผู้จัดการเรียกดูรายงานมูลค่าสต็อกแยกตามหมวดหมู่
  Then หมวด "ประปา" ต้องแสดงมูลค่ารวม 0.0 บาท
```

### AC ของ US-04: กำหนดค่า threshold แยกรายสินค้า
```gherkin
Scenario: กำหนดค่า threshold รายสินค้าสำเร็จ
  Given สินค้า "หลอดไฟ LED" มี threshold ปัจจุบันเท่ากับ 10 ชิ้น
  When ผู้จัดการทำการแก้ไขค่า threshold ใหม่เป็น 25 ชิ้น
  Then ค่า threshold ของสินค้า "หลอดไฟ LED" จะต้องถูกอัปเดตเป็น 25 ชิ้น
  And การจ่ายสินค้าครั้งถัดไปจะนำเกณฑ์ 25 ชิ้นนี้ไปใช้ในการตรวจสอบสต็อกต่ำทันที

Scenario: ปฏิเสธการกำหนดค่า threshold ที่เป็นค่าลบ
  Given สินค้า "หลอดไฟ LED" มี threshold ปัจจุบันเท่ากับ 10 ชิ้น
  When ผู้จัดการพยายามกำหนดค่า threshold เป็น -5 ชิ้น
  Then ระบบต้องปฏิเสธการตั้งค่าและแสดงข้อความแจ้งเตือนความผิดพลาด
  And ค่า threshold ของสินค้ายังคงเป็น 10 ชิ้นเท่าเดิม
```

### AC ของ US-05: เลือกลงทะเบียนช่องทางการแจ้งเตือน
```gherkin
Scenario: ลงทะเบียนรับการแจ้งเตือนพร้อมกันทั้ง Email และ SMS
  Given ผู้จัดการลงทะเบียนทั้ง EmailNotifier และ SMSNotifier เข้าสู่ระบบ InventoryService
  When มีการจ่ายสินค้าจนสต็อกคงเหลือต่ำกว่าเกณฑ์ threshold
  Then ระบบต้องส่งข้อความแจ้งเตือนจำลองออกทางคอนโซลทั้งช่องทาง Email และ SMS พร้อมกัน

Scenario: ลงทะเบียนรับการแจ้งเตือนเพียงช่องทางเดียว
  Given ผู้จัดการลงทะเบียนเฉพาะ EmailNotifier ไว้ในระบบ
  When มีการจ่ายสินค้าจนสต็อกคงเหลือต่ำกว่าเกณฑ์ threshold
  Then ระบบต้องส่งข้อความแจ้งเตือนจำลองออกเฉพาะช่องทาง Email เท่านั้น และต้องไม่มีข้อความจาก SMS ปรากฏ
```

## 4. In Scope / Out of Scope
* **In Scope:** บันทึกรับ/จ่าย + อัปเดตสต็อกใน memory, แจ้งเตือน Email/SMS (จำลองด้วย print), รายงานมูลค่าแยกหมวด, กำหนด threshold รายสินค้า, ลงทะเบียนช่องทางแจ้งเตือนได้หลายช่องทางพร้อมกันผ่าน Observer Pattern
* **Out of Scope:** ส่ง Email/SMS จริงผ่านเครือข่าย, ระบบล็อกอิน/สิทธิ์, ฐานข้อมูลถาวร (ใน lab นี้จัดเก็บข้อมูลใน memory ชั่วคราว ไม่บันทึกลง Database จริง)

## 5. Functional Requirements (FR)

| รหัส | ความต้องการ | จาก Story |
|---|---|---|
| FR-01 | ระบบต้องอัปเดตสต็อกทันทีหลังบันทึกรับ/จ่าย | US-01 |
| FR-02 | ระบบต้องตรวจสต็อกก่อนจ่าย และปฏิเสธถ้าไม่พอ | US-01 |
| FR-03 | ระบบต้องแจ้งเตือนเมื่อสต็อกหลังจ่ายต่ำกว่า threshold | US-02 |
| FR-04 | ระบบต้องคำนวณผลรวม (สต็อกคงเหลือ x ราคาต่อหน่วย) จัดกลุ่มตามหมวดหมู่สินค้า | US-03 |
| FR-05 | ระบบต้องรองรับการกำหนดค่า threshold สำหรับสินค้าแต่ละรายการ | US-04 |
| FR-06 | ระบบต้องรองรับการลงทะเบียนช่องทางการแจ้งเตือนได้หลายช่องทางพร้อมกัน | US-05 |

## 6. Non-Functional Requirements (NFR)

| รหัส | มิติ | ความต้องการ (ต้องวัดได้) |
|---|---|---|
| NFR-01 | Performance | รายงานมูลค่าสต็อก 1,000 รายการเสร็จภายใน 1 วินาที |
| NFR-02 | Maintainability | เพิ่มช่องทางแจ้งเตือนใหม่ได้โดยไม่แก้ business logic เดิม |
| NFR-03 | Reliability | ระบบต้องทำงานถูกต้อง ไม่ส่งการแจ้งเตือนผิดพลาดเมื่อสต็อกเท่ากับ threshold พอดี |

## 7. Design Notes
* การแจ้งเตือนต้องแยกออกจาก business logic ของสต็อก
* คาดว่าจะมีหลายช่องทางแจ้งเตือน ออกแบบให้เพิ่มได้ง่าย (ใช้ Factory Pattern และ Observer Pattern)
